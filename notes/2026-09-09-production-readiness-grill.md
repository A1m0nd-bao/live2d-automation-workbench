# Live2D 工作台生产就绪度：Grill / Discovery Notes

Date: 2026-09-09 · Goal: 明确工作台进入实际生产前的交付标准、风险边界与优先级，并将已确认事项落入可执行的验收清单。

## Summary / key decisions

- 目标不是个人演示工具，而是支撑公司内部稳定创作需求的基础设施。
- 成品验收（Cubism 可打开、全参数不破图、运行时可用）仍在建设中，暂不作为本轮已解决项。
- 除成品验收外，资产留存与版本、任务可恢复、质量门禁、服务可靠性、权限与审计都需要纳入生产化范围。
- 资产采用最小可见范围：创作者仅能查看自己的项目；管理员拥有全量项目、日志、配置与审核可见性。
- 首期团队规模低于“10 位创作者、20–50 个任务／日、2–3 并发”的预估；不需要高并发集群，但任务仍须脱离浏览器持久运行并可恢复。
- 可以接受计划内短暂维护；已提交任务与已产出资产必须在服务恢复后保留，并支持自动续跑或管理员一键重跑。
- 正式项目的原图、预处理图、PSD 与 CMO3 长期保留；失败中间文件与详细日志保留 30 天；管理员可按项目删除并留下审计记录。
- 上传后任务自动连续推进；只有 CMO3、运行时包与验收报告齐备后，才进入管理员“通过／退回／重跑”的验收状态。
- 第三方服务或 PSD 质量失败时，同一阶段最多自动重试两次；仍失败冻结任务、保留上下文并通知管理员；管理员可按原参数重跑、从失败阶段重跑，或退回创作者补图。
- 管理员提醒的第一入口是工作台内待办与红点；不以个人聊天通知作为任务状态的唯一来源。
- 产品不依赖飞书；身份、权限、部署与展示能力均须独立于公司体系。
- 独立账号采用邮箱登录；生产任务入口受账户与角色控制。
- 账号仅由管理员邀请创建，避免公开注册滥用服务与模型额度。
- 模型调用成本当前很低；用户倾向先将资产放在 GitHub。经核对，GitHub 适合代码与版本化清单，但不适合作为原图、PSD、CMO3、日志的生产资产库：普通 Git 拒绝超过 100 MiB 的文件，LFS 不适用于 GitHub Pages 且二进制版本会累积存储与流量。
- 正式二进制资产可改用 S3 兼容对象存储；工作台通过有时效、按权限的下载链接交付，GitHub 继续负责代码、配置与展示资产。
- 产品保持单一网址、单一体验：公开访问者只读展示，邮箱登录后进入私有工作区与真实任务；GitHub Pages 可继续承载前端，但生产数据、密钥与队列必须由受控后端提供。
- 后端选择 Supabase，承载邮箱登录、项目数据库、对象存储和权限；常驻生成 Worker 通过受认证 API 调用。创作者不需要处理服务地址、密钥或文件搬运。
- 创作者日常路径收敛为登录、新建项目、上传、离开后等待结果、查看结果或管理员退回意见；不暴露连接检查、服务地址或逐步推进按钮。管理员额外处理待办、失败、重跑和验收。
- 第一版不扩展多人协作、客户外发、付费、公开投稿、移动端或额外合规范围；集中完成私有创作、自动任务、管理员验收和可靠资产留存。

## Q&A log

### Q1 — 生产的最低定义

- Asked: 你希望“可进入生产”的最低标准是什么？
- Captured: “成品验收这一步我还在做，其他的这几个我确实没有去想过，我希望他能够支撑的起一个公司内部的稳定创作需求”。
- Decision: 以公司内部稳定创作基础设施为目标，而非仅单人演示或单次出图；成品验收另行持续建设。
- Flags: 成品验收的具体通过规则尚未定义 -> 用户与 Cubism 验收流程。

### Q2 — 公司内部的资产可见范围

- Asked: 公司内部时，作品和任务默认应如何可见？
- Captured: “符合方式，只有管理员看到是应该的”。
- Decision: 创作者仅查看自己的项目；管理员可查看全量资产、任务日志与配置，并承担审核侧职责。项目之间不默认互相可见。
- Flags: 无。

### Q3 — 第一阶段的使用规模

- Asked: 第一阶段你预计的使用规模大概是什么？
- Captured: “会比这个少一些”。
- Decision: 首期按小团队、低并发设计；优先投入持久队列、任务恢复、资产存储和管理员监控，而非高并发扩容。
- Flags: 日任务量与同时运行数尚未量化 -> 用户。

### Q4 — 维护与故障恢复

- Asked: 你能接受每次更新或外部模型故障时，工作台有短暂维护窗口吗？
- Captured: “能接受”。
- Decision: 首期允许计划内短暂停用；已提交任务必须持久保存，服务恢复后自动继续或可由管理员一键重跑。
- Flags: 无。

### Q5 — 资产保留与删除

- Asked: 原图、预处理图、PSD、CMO3 与日志要保留多久？
- Captured: “按你的建议来吧”。
- Decision: 正式项目资产长期保留；失败中间文件与详细日志保留 30 天；删除由管理员执行并产生审计记录。
- Flags: 长期留存的最终存储配额与备份周期待实施时确定 -> 管理员。

### Q6 — 自动推进与人工关卡

- Asked: 一条任务在正式环境里，应该在哪一步停下来等人工确认？
- Captured: “符合”。
- Decision: 上传后所有处理自动连续推进，不要求创作者逐步点击；CMO3、运行时包和验收报告生成后进入待管理员验收，管理员可通过、退回或重跑。
- Flags: 无。

### Q7 — 外部服务失败策略

- Asked: 第三方生成服务超时、返回不合格 PSD，或模型临时不可用时，你希望系统怎么处理？
- Captured: “建议的没毛病”。
- Decision: 每阶段自动重试两次；仍失败则冻结任务且保留上下文。管理员可原参数重跑、从失败阶段重跑或退回创作者补图；不静默跳过，也不交付半成品。
- Flags: 无。

### Q8 — 管理员提醒渠道

- Asked: 管理员在任务冻结、需要验收、或重跑失败时，应该在哪里收到提醒？
- Captured: “建议的没毛病”。
- Decision: 首期以工作台内管理员待办与红点提醒为唯一任务状态入口；飞书等外部通知留待后续补充。
- Flags: 无。

### Q9 — 身份体系与产品独立性

- Asked: 公司内部是否以飞书账号作为身份体系？
- Captured: “是用的飞书体系，但是我不想让这个项目完全依附于公司，也有个人展示的想法”；后续明确“都不依靠飞书可以吗”。
- Decision: 产品不接入、也不依赖飞书。采用独立帐号、角色与审计模型，内部与个人展示均可脱离公司体系运行。
- Flags: 无。

### Q10 — 独立帐号登录方式

- Asked: 独立账号体系用什么登录方式？
- Captured: “邮箱登陆吧”。
- Decision: 使用邮箱登录；生产任务由应用内账号与角色控制，不依赖飞书或公司身份供应商。
- Flags: 无。

### Q11 — 账号创建策略

- Asked: 邮箱账号是任何人自助注册，还是只能由管理员邀请创建？
- Captured: “建议的没毛病”。
- Decision: 首期采用管理员邀请制的邮箱帐号；不开放自助注册。
- Flags: 无。

### Q12 — 成本与资产存储

- Asked: 模型调用和存储成本，需要怎样控制？
- Captured: “调用现在成本很低，存储先扔GitHub上”。
- Decision: 首期不以调用额度为主要约束。GitHub 保留为代码、部署和资产清单／发布记录的版本库；正式二进制资产库的落点需要改为对象存储。
- Flags: 无。

### Q13 — 正式资产库

- Asked: 你接受把正式二进制资产放到独立对象存储吗？
- Captured: “可以”。
- Decision: 原图、预处理图、PSD、CMO3、运行时包和日志附件存入 S3 兼容对象存储；工作台以带时效、受权限控制的链接提供下载。GitHub 仅保存代码、流程配置、资产清单、验收报告和可公开展示内容。
- Flags: 无。

### Q14 — 展示与生产是否分开部署

- Asked: 你接受把“生产工作台”和“GitHub Pages 展示页”分开部署吗？
- Captured: “不接受”。
- Decision: 用户不希望展示与生产体验成为两个割裂的部署／产品。需要采用单产品、单域名的公开展示与受保护工作区模式。
- Flags: 无。

### Q15 — 单一产品体验的含义

- Asked: 你说“不接受”，是指希望用户看到的是同一个网址、同一套产品体验，还是指生产系统也必须继续只托管在 GitHub Pages？
- Captured: “建议的没毛病”。
- Decision: 同一个域名与产品体验；游客默认只读展示，邮箱登录后解锁私有项目和真实任务。前端可保留 GitHub Pages，后端能力独立但不呈现为另一个产品。
- Flags: 无。

### Q16 — 托管后端选择

- Asked: 你接受使用一个独立的托管后端来提供邮箱登录、数据库与对象存储吗？
- Captured: “ok啊就用这个吧，但是你要保证我调用时方便”。
- Decision: 使用 Supabase 提供邮箱登录、数据库、对象存储与权限。GitHub Pages 保持为同一前端入口；生成 Worker 通过认证 API 访问后端。易用性是硬约束，创作者不操作服务地址、Token、连接检查或手工文件转移。
- Flags: Supabase 项目创建与密钥配置需在实施时由用户完成或授权 -> 用户。

### Q17 — 创作者与管理员工作流

- Asked: 创作者的日常操作是否应收敛成“登录 → 新建项目 → 上传图 → 离开页面也可继续 → 回来查看结果或管理员退回意见”？
- Captured: “建议的没毛病”。
- Decision: 创作者仅执行项目创建与上传，任务在后台自动推进；管理员负责待办、失败原因、重跑和验收。生产模式不展示“连接服务”“检查服务”“继续下一步”等运维按钮。
- Flags: 无。

### Q18 — 第一版范围完整性

- Asked: 除了成品验收规则外，有没有任何必须第一版就支持的事情——例如多人协作、客户外发、付费、公开投稿、移动端、或特定合规要求？
- Captured: “没有完全没有”。
- Decision: 第一版不纳入上述扩展能力；范围锁定为私有创作、自动任务、管理员验收与可靠资产留存。
- Flags: 无。
